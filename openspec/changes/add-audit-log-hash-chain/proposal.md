## Why

A pitch-accuracy review (research into NIST AI RMF, EU AI Act Article 12, and a common 12-field AI-audit-trail checklist, verified against the real code — not the pitch deck) found that `AuditLogEntry` (`pipeline/models.py`) already substantively matches what's expected of a trustworthy AI audit trail: a unique id, the contract and clause it belongs to, the pipeline stage, the exact prompt version, the raw model response, the model name, latency, and a timestamp, written from exactly one place per stage (`pipeline/services.py` for stages 1-3, `razorpay_integration/services.py` for stage 4, `risk_scoring/services.py` for stage 5). One concrete gap remains: none of it is tamper-evident. Today, nothing stops a row's `llm_response_raw` or `stage` from being edited after the fact, or a row from being deleted, and nothing would show it happened. That is the single most common follow-up question a skeptical auditor or judge asks of an "audit trail" — not "do you log it" but "can you prove it wasn't changed."

This product's core differentiator is already built around *provable, not just claimed*: `razorpay_integration`'s no-write-calls guarantee is not stated in a system prompt or a comment, it is checked live by `reporting.selectors.scan_razorpay_guardrail` (an AST scan of the actual current source) and surfaced through both a management command (`report_ui/management/commands/verify_guardrail.py`) and a live page (`report_ui/templates/report_ui/guardrail_verification.html`) that reruns the scan on every load. A hash-chained audit trail is the same idea applied to the audit log itself: instead of asking a reader to trust that `AuditLogEntry` rows are intact, give them a command that recomputes the chain from the raw data and says PASS or FAIL, deterministically, every time.

**Non-goals**: this does not change what is logged - no new fields carrying business content, no change to stage numbering, prompt versions, or which events get an audit entry. It does not build any UI for editing or diffing audit history, and it does not add cryptographic signing, external timestamping, or anchoring the chain to anything outside this database - pure in-database hash-chain tamper evidence is the entire scope. It does not retroactively prove that rows written before this change was applied were never edited - see design.md (Decision: Backfill) for why that claim cannot honestly be made and is deliberately not attempted.

## What Changes

- `pipeline.models.AuditLogEntry` gains three nullable fields: `prev_hash`, `entry_hash` (64-character hex SHA-256 digests) and `chain_sequence` (a per-contract monotonic integer). One new migration adds the columns only - no data migration computes hashes for existing rows (see design.md - Decisions).
- New `core/audit_hash.py`: a small, model-free module holding `GENESIS_PREV_HASH` and the one `compute_entry_hash(...)` function that defines the canonical serialization and hashing rule. This is the single source of truth both the writer and the verifier call - never two independent implementations of the same formula.
- `pipeline.services._create_audit_log_entry` is promoted to a public `create_audit_log_entry(...)` and becomes the *only* place `AuditLogEntry.objects.create(...)` is called anywhere in the codebase. `razorpay_integration/services.py` and `risk_scoring/services.py` each delete their own private `_create_audit_log_entry` duplicate and call `pipeline.services.create_audit_log_entry(...)` directly at their existing call sites (stage 4's `_generate_mismatch_description`; stage 5's `score_clause` short-circuit and main paths), passing their own stage number and prompt version exactly as before.
- `pipeline.selectors` gains `get_chain_tip(*, contract)`, used by the writer to look up the current end of a contract's chain.
- `reporting.selectors` gains `verify_audit_chain(*, contract=None)`, mirroring `scan_razorpay_guardrail`'s dataclass-result, recompute-don't-trust pattern: it re-derives every entry's expected hash via `core.audit_hash.compute_entry_hash` and reports exactly where (if anywhere) the persisted chain diverges from that.
- New management command `report_ui/management/commands/verify_audit_chain.py`, mirroring `verify_guardrail.py`'s shape: thin wrapper around `reporting.selectors.verify_audit_chain`, non-zero exit (`CommandError`) on any detected break.
- `report_ui`'s existing per-contract audit log page (`contract_audit_log_view` / `contract_audit_log.html`) gains a small chain-integrity section computed by calling the exact same `verify_audit_chain(contract=...)` the CLI command calls - no separate "is this trustworthy" logic duplicated between the page and the command.
- `reporting.serializers.AuditLogEntrySerializer` gains the three new fields (additive, non-breaking) so the existing DRF audit-log endpoint and the `frontend/` TypeScript types can display the same chain data the Django template and CLI expose.

## Capabilities

### New Capabilities
- `pipeline/audit-log-integrity`: every `AuditLogEntry` write is hash-chained to the prior entry for its contract, and the chain's integrity is deterministically, independently re-checkable via a management command rather than merely asserted.

### Modified Capabilities
(none declared - no prior change has been archived yet, so there is nothing under `openspec/specs/` to declare a delta against; same constraint noted in `close-pitch-accuracy-gaps`.)

## Impact

- **Changed code**: `pipeline/models.py` (+ new migration), `pipeline/services.py`, `pipeline/selectors.py`, `razorpay_integration/services.py`, `risk_scoring/services.py`, `reporting/selectors.py`, `reporting/serializers.py`, `report_ui/views.py`, `report_ui/templates/report_ui/contract_audit_log.html`, `pipeline/tests/factories.py` (new fields default to `None`, matching the exemption convention).
- **New code**: `core/audit_hash.py` (+ `core/tests/test_audit_hash.py`), `report_ui/management/commands/verify_audit_chain.py`.
- **No impact** on any pipeline, cross-check, or scoring *decision* logic - `AuditLogEntry.stage`, `prompt_version`, `llm_response_raw`, `model_name`, and `latency_ms` are populated exactly as before; this change only adds three new columns and a verification path around the existing write. No previously-passing test's assertions about pipeline outputs should change; tests that construct an `AuditLogEntry` via `AuditLogEntryFactory` continue to work unchanged since the new fields are nullable.
- **Frontend**: `frontend/src/api/types.ts`'s audit-log entry type gains the three optional fields to stay accurate to the DRF response; rendering them in the React UI is not required by this change (mirrors the "type must exist and be accurate, rendering it is not in scope" precedent from `close-pitch-accuracy-gaps`).
