## Why

`razorpay_integration`'s stage-4 cross-check already compares a contract's stated `payout_frequency` cadence against the *empirical* cadence derived from historical Payout records (median of consecutive deltas), producing a persisted `cadence_mismatch` MismatchFlag when the two disagree by more than `CADENCE_MISMATCH_TOLERANCE_RATIO`. That answers "does the contract's stated cadence match the platform's observed history so far" - a backward-looking question, decided once, at pipeline-run time. It does not answer a different, forward-looking question a reviewer actually cares about the moment they open a report: "is this vendor's next payout already late, right now?" A contract can pass every persisted cross-check the day the pipeline runs and still be sitting on a missed payout three weeks later - nothing re-evaluates it, because nothing re-runs the pipeline just because a calendar date passed.

**This is why overdue detection must be a live, request-time computation, never a persisted `MismatchFlag`, and must never run inside `detect_mismatches` (stage 4).** "Overdue" is a function of `django.utils.timezone.now()` at read time, not of any new analysis - a contract that is not overdue today becomes overdue next week with zero new pipeline activity, zero new extraction, zero new Razorpay data. Writing it as a MismatchFlag during stage 4 would freeze a verdict that is true only at the instant the pipeline happened to run, and it would go stale the moment the calendar moved past it - silently wrong, with nothing to invalidate it, for every day between pipeline runs. The only way to keep the verdict honest is to recompute it every time it's read, from data that already exists: `ExtractedTerm` rows and `PlatformRecord` rows a prior real stage-4 run already fetched and persisted. This is the exact same "recompute-don't-trust" shape this product has already used twice - `reporting.selectors.scan_razorpay_guardrail` (recomputes a static-scan verdict on every call, never cached) and `reporting.selectors.verify_audit_chain` (recomputes a hash-chain verdict on every call, never cached) - applied to a third kind of live-checkable claim.

Because this reads only rows a prior stage-4 run already persisted, it issues **zero new Razorpay API calls** and is fully unit-testable without `ENABLE_STAGE_4` or real Razorpay keys - the same testability property every other selector-layer read in this codebase already has.

**Reuses `CADENCE_MISMATCH_TOLERANCE_RATIO` rather than introducing a new setting.** The persisted cadence_mismatch check and this live overdue check are both instances of the same underlying question - "does the observed gap between payouts stay within an acceptable band around the contract-stated interval?" - just evaluated at two different reference points (a *median* of historical gaps vs. the *single* gap since the most recent payout). A second, independently-tunable tolerance for what is conceptually the same slack allowance would let the two checks silently disagree about how much lateness is acceptable for the exact same contract, with no principled reason for them to differ - one tolerance knob per comparison *kind* (cadence vs. amount), not one per code path that happens to compare a cadence, is this project's existing convention (see add-razorpay-route-crosscheck's Migration Plan: "no route-specific tolerance setting is introduced, keeping one tolerance knob per comparison kind"). This change follows that same rule rather than inventing an exception for itself.

## What Changes

- **Refactor (prerequisite):** promote `_is_cadence_term`, `_is_amount_term`, `_term_unit`, `_term_numeric_value`, `_TIME_UNITS`, and `_DAYS_PER_UNIT` from `razorpay_integration/services.py` (private) to `razorpay_integration/selectors.py` (public, no leading underscore). These are pure reads/classifications over an already-persisted `ExtractedTerm.value_structured` - they belong in the reads module per this project's established services.py-writes / selectors.py-reads convention, the same reasoning add-audit-log-hash-chain already applied when it consolidated the three duplicate `_create_audit_log_entry` write helpers into one shared function. `services.py` imports these from `selectors.py` instead of defining its own copies. No behavior change - only location and visibility. `_PERIOD_BY_UNIT` (used only by the subscription-path exact-config-diff comparison, unrelated to cadence-vs-amount classification) stays private in `services.py`.
- Add `razorpay_integration.selectors.OverdueStatus` (a frozen dataclass: `term_id`, `is_overdue`, `days_since_last_payout`, `expected_interval_days`, `latest_payout_date`) and `razorpay_integration.selectors.list_overdue_statuses(*, contract) -> list[OverdueStatus]`: for each of a Payout-referenced Contract's cadence-type `payout_frequency` ExtractedTerm rows, computes `is_overdue` live from that Contract's existing Payout `PlatformRecord` history and `CADENCE_MISMATCH_TOLERANCE_RATIO`. Returns `[]` for a Subscription-referenced Contract, for an amount-type `payout_frequency` term, and for a Contract with zero Payout PlatformRecords (that "no evidence at all" case is already `missing_platform_evidence`'s job at analysis time - this must not duplicate or contradict it). Returns one entry per qualifying term, since a contract can have more than one payment-schedule clause (or more than one cadence term within one clause).
- Wire `list_overdue_statuses` into `reporting.selectors.get_contract_reasoning_chain`: `ClauseReasoningChain` gains an `overdue_statuses: list[OverdueStatus]` field, populated with the `OverdueStatus` entries whose `term_id` belongs to that clause's `extracted_terms` (empty list otherwise) - the same per-clause, always-present-possibly-empty-list convention `mismatch_flags` and `verified_platform_records` already establish on that same dataclass.
- Add `reporting.serializers.OverdueStatusSerializer` and an `overdue_statuses` field on `ClauseReasoningChainSerializer`, mirroring the dataclass field-for-field.
- Add the matching `overdue_statuses: OverdueStatusEntry[]` field to `frontend/src/api/types.ts`'s `ClauseReasoningChain` interface, and render a warning banner in `ContractDetailPage.tsx`'s reasoning-chain view (per extracted term, when `is_overdue` is true) reusing the existing `--color-warning*` banner pattern `.needs-review-banner` already established, rather than inventing new CSS.

## Capabilities

### New Capabilities

- `razorpay-integration/overdue-payment-detection`: live, request-time detection of whether a Payout-referenced Contract's next payout is already overdue, computed from already-persisted `ExtractedTerm` and `PlatformRecord` rows on every read - never persisted as a MismatchFlag, never computed during stage 4, issuing zero Razorpay API calls.

### Modified Capabilities

(none - no prior change has been archived yet, so there is nothing under `openspec/specs/` to declare a delta against; same constraint noted in add-audit-log-hash-chain and close-pitch-accuracy-gaps.)

## Impact

- `razorpay_integration/selectors.py`: gains `term_unit`, `term_numeric_value`, `is_cadence_term`, `is_amount_term`, `TIME_UNITS`, `DAYS_PER_UNIT` (promoted from `services.py`, public), plus the new `OverdueStatus` dataclass and `list_overdue_statuses` selector.
- `razorpay_integration/services.py`: the six promoted names are removed; every call site (`_run_payout_crosscheck`, `_evaluate_cadence_term`, `_evaluate_amount_term`, `_run_subscription_crosscheck`, `_evaluate_subscription_cadence_term`, `_evaluate_subscription_amount_term`) is updated to call `razorpay_selectors.<name>` instead - a mechanical rename, no behavior change. `detect_mismatches` and every persisted MismatchFlag code path are otherwise untouched.
- `razorpay_integration/tests/`: any existing test that referenced the promoted helpers by their private names is updated to the public names (none currently do, per a repo-wide search before writing this proposal); new `TestListOverdueStatuses` coverage added to `test_selectors.py`.
- `reporting/selectors.py`: `ClauseReasoningChain` gains `overdue_statuses`; `get_contract_reasoning_chain` calls `razorpay_selectors.list_overdue_statuses` once per contract and distributes each result to its owning clause by `term_id`.
- `reporting/serializers.py`: new `OverdueStatusSerializer`; `ClauseReasoningChainSerializer` gains the matching field.
- `reporting/tests/`: new coverage confirming `overdue_statuses` appears correctly on both the selector and serializer output.
- `frontend/src/api/types.ts`: new `OverdueStatusEntry` interface; `ClauseReasoningChain.overdue_statuses` field.
- `frontend/src/pages/ContractDetailPage.tsx` (+ its test file): renders an overdue warning banner per affected extracted term.
- `frontend/src/index.css`: no new banner shape - reuses the existing `--color-warning*` tokens and pill-banner pattern already established by `.needs-review-banner`/`.confirmed-banner`.
- **No change** to `razorpay_integration.services.detect_mismatches`, to any persisted `MismatchFlag` type, to `ENABLE_STAGE_4` gating, or to `pipeline.services.run_pipeline` - this capability is reachable with zero pipeline runs beyond whatever real stage-4 run already populated the `PlatformRecord` rows it reads.
- **No new Django setting** - `CADENCE_MISMATCH_TOLERANCE_RATIO` is reused as-is; see Why, above.

**Non-goals**: this change does not compute overdue status for amount-type `payout_frequency` terms (a flat amount has no interval to be "late" against - out of scope, not silently skipped: see design.md and the spec's explicit scenario), does not compute it for Subscription-referenced Contracts (a Subscription's cadence is diffed by exact config field against a Razorpay-side setting, not derived empirically from history - a fundamentally different comparison this capability does not attempt to generalize to), does not persist any result, does not create a MismatchFlag or any other new database row, and does not change risk scoring, the evaluation harness, or any existing stage-4 cross-check path.
